# トラック 8 — 画面の点検（ログイン後に主要な画面が壊れていない）

> 記法は [`../README.md`](../README.md)。範囲: ログイン後に開く主要な画面 5 枚（`/hub`・`/hub/faq`・`/desk`・`/files`・`/settings`）が、開いて中身が描き上がること。
> 対象外: 画面上の操作の結果（→ 各トラックの画面操作要領）、見た目（色・並び・重なり）の良し悪し（→ 画面の部品の試験）。

## 0. このトラックの性格

**通信ではなく画面そのものを見る**。ここまでの E2E は API の応答だけを確かめており、画面が白くなっても緑のまま通った
（実測 2026-10-25: 画面 6 枚が 500 で真っ白の間に、シナリオは緑と記録された・d784）。このトラックは実ブラウザで画面を開き、
「白い画面」「殻だけの画面」「例外の枠」「止まった通信」「極端に遅い描き上がり」を 1 か所で捕まえる。

見るのは **壊れていないこと** だけで、画面の中身の正しさ（何が並ぶか・どこへ遷移するか）は各トラックが持つ。

## 2. ケース

### S-SCR-01-C1 主要な画面 5 枚を実ブラウザで開く（自動）

| 項目   | 内容                                                                                                                                                                        |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 前提   | rete の backend（`127.0.0.1:3011`）と frontend（`localhost:3010`）が稼働している。管理者のセッションは事前生成したものを使う                                                |
| 手順   | 1. 管理者のセッションを画面の置き場へ向けてブラウザを開く<br>2. `/hub`・`/hub/faq`・`/desk`・`/files`・`/settings` を順に開き、描き上がりを待つ                             |
| 期待   | どの画面も ①本文が描き上がる（空・例外の枠・殻だけにならない） ②ホームは掲示板・カレンダー・FAQ の行き先が出る ③画面の実行時エラー・止まった通信が無い ④15 秒を超えていない |
| 後始末 | なし（画面を見るだけでデータを作らない）                                                                                                                                    |
| 実行   | 自動 `@S-SCR-01` `@S-SCR-02` `@S-SCR-03`（`zz-screen.feature`・project `screen`）                                                                                           |

### S-SCR-04-C1 画面の中身が作れなかった時に「壊れている」と分かる

| 項目   | 内容                                                                                                                                                                                  |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 前提   | 画面を表示する処理が例外で落ちる（同期の描画例外）。中身の取得が失敗するだけの時は、各画面の既存の扱い（空表示など）になり、この表示は出ない                                          |
| 手順   | 1. その画面を開く<br>2. 表示と、もう一度表示する操作を確かめる                                                                                                                        |
| 期待   | ①「この画面は壊れています」の表示が出る（白いまま止まらない） ②「もう一度表示する」で開き直せる ③例外の中身は本文に出ない ④原因はブラウザのコンソールへ記録される                     |
| 後始末 | なし                                                                                                                                                                                  |
| 実行   | 自動 `packages/frontend/src/app/__tests__/screen-broken.test.tsx`（表示の振る舞い）。主要 5 枚では、それぞれを開いた時点で「壊れている」表示が出ていないことを `zz-screen` が確かめる |

実機での確認（2026-10-26）: `/hub/calendar` の組み立てを一時的に例外で落として開き、「この画面は壊れています」・識別子・
「もう一度表示する」が出ることと、画面の道筋・例外・識別子がコンソールへ残ることを確かめた（証跡は `tmp/d785/shots/`）。
同じ日、`/hub/faq` を落とした状態で `zz-screen` が赤になること（2 枚目の破損を取り逃がさないこと）も実測した。

**実行の記録（2026-10-27・d825）**

| ケース       | 走らせたもの                                                         | 結果                                   |
| ------------ | -------------------------------------------------------------------- | -------------------------------------- |
| S-SCR-01〜03 | `zz-screen.feature`（project `screen`）                              | 緑（所要は回ごとに 22〜32 秒で変わる） |

5 枚の画面で「壊れています」の表示が出ていないことは、`zz-screen` の「どの画面も白くなっていない」の手順の中で
確かめている（`e2e/steps/screen.steps.ts` が `data-screen-broken` を控え、空であることを判定する）。

同じ並びで走る `zz-files-screen`（ファイルトラックの d821）は S-FILE-14 と S-FILE-04-C2 を持つ。S-FILE-04-C2
（一覧の行をツリーのフォルダへ落として移す）は d862 で道を足した。ケースの正本は `04-files.md`。

**対象から外した画面**

- カレンダー（`/hub/calendar`）: 開発機の起動直後の初回だけ画面の組み立て準備で 35 秒前後かかり（実測 2026-10-26）、
  「遅い画面」の判定と混ざる。2 回目以降は 10 秒未満で開く。起動直後に確かめたい時は手で開く。
- ログイン画面（`/login`）: セッションの有無に依らず開くので、この feature の前提（ログイン済み）と関係しない。

**見つけた、このトラックの所管外の問題（2026-10-27・d825）**

画面を実ブラウザで動かして確かめる中で、ファイル画面の移動について次のことを実測した（2026-10-27 の時点の姿）。

- 当時の何が起きるか: 一覧の行を掴んでツリーのフォルダへ運び、その上で離しても、ファイルは移らなかった（移動の要求が出ない）。
  画面は「移し先の上で離した」とだけ記録し、利用者から見ると**何も起きない**状態だった。
- 当時のなぜか: 画面が掴んだ物と落とす先の組み合わせのうち三通り（ツリーのフォルダ → ツリーのフォルダ／一覧の行 →
  一覧のフォルダの行／検索結果 → ツリーのフォルダ）だけを移動として扱い、「一覧の行 → ツリーのフォルダ」を
  扱っていなかった。
- 当時の別の道: 移動そのものは画面からもできた。一覧の中でフォルダの行の上へ落とす道と、検索結果からツリーへ落とす道。
  届かなかったのは「一覧の行をツリーへ落とす」この一つだった。
- 当時の手引きとの差: 手引き（`04-files.md` の S-FILE-04）は「`/files` → 行をドラッグして別フォルダへ」とだけ書き、
  どの落とし方が動くかを分けていなかったため、利用者はこの届かない道を先に試す。
- 当時の直した側: ドラッグ中に指へ付いてくるラベルが、落とす先の上でポインターを受け止めていた点は直した
  （表示だけの層としてポインターを素通しにした）。これは上記とは別の不具合だった。
- どうするか: 2026-10-28 に道を足した（d862・`04-files.md` の S-FILE-04-C2）。画面は「一覧の行 → ツリーのフォルダ」も
  移動として扱い、移した行は移し先の一覧へ移る。画面の現在地（パンくず）は移す前のフォルダのままで、続けて別の行を
  移せる。
