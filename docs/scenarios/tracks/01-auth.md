## 3. このトラックの未確定事項

### SSO 往復の試験が何を確かめ、どこまでを確定とするか（d844）

S-AUTH-04・05 は `e2e/ui/sso.spec.ts`（project `ui-sso`）が担う。**確定とするのは、画面が次へ着地したことまで**。

| 経路      | 確定とする（試験が緑で決まる）                                                                                            | 確定としない（人が画面で見る）                                       |
| --------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| S-AUTH-04 | rete にログインした同じブラウザで reference の `/login` を開くと、入力欄を描かず `/home` に着地し、ログアウト操作が見える | 同意画面が将来出るかは画面の作りで変わる（出れば入力欄待ちで落ちる） |
| S-AUTH-05 | reference の `/login` から rete の `/login?uid=` へ回り、資格情報を入れると reference の `/home` に着地する               | 業務用の資格情報で本人の権限が引けるか（試験は管理者 1 名で回す）    |

- **前提外では赤にしない**（reference に 5 秒で届かない時は skip）。その時は ✅ を維持し、直近の実行が skip だったことをこの節に残す。
- 「同意画面が出ないこと」は、着地面 `/home` とログアウト操作の出現で見分ける（同意画面に止まれば着地しない）。
- 回し方: `cd e2e` → `npm run test:ui`（rete 3010/3011 と reference 3000/3001 が起動していること、ホストは `localhost` 固定）。
- 回す前に、reference の開発 DB が種データどおりであることを見る。種データが消えていると（`admin@rete.local` の sub が role なし・停止中で残る）、SSO は失敗せず reference の `/pending` に着地し、試験は「`/home` に来ない」で落ちる。**この赤はコードの退行ではなく前提の欠け**なので、`pnpm --filter @struct-pass/backend run prisma:seed` で種データを戻してから回し直す（reference は種データが毎回の土台なので、戻すのは前提の復元であって結果の作り直しではない）。
- 2026-10-28 の実行で 2 本とも緑（9.5 秒）。これで S-AUTH-04・05 の ✅ を出し直した。
- 同じ日の再実行で、種データの欠けによる赤（着地先 `/pending`）を実測。種データを戻した後に 2 回連続で緑（11.0 秒・8.4 秒）を確かめた。

### このトラックの論点

| 論点                                                   | 影響             | 決める場所                   |
| ------------------------------------------------------ | ---------------- | ---------------------------- |
| パスワードポリシー違反の弾く場所と文言                 | 受諾時の離脱     | 決定                         |
| ロック解除の経路（自動か管理者のみか）と利用者への案内 | 問い合わせ増     | 決定                         |
| SSO の同意画面を毎回出すか                             | 日常の往復コスト | 決定（現在は初回のみを想定） |

- MFA 強制の挙動は実測で決まった（S-AUTH-08: ログインは通し、業務 API を 403 で塞ぎ、画面は設定へ送る）。
- パスワードの下限は受諾の入口（`POST /invites/accept`）で弾く（S-AUTH-11・422 で理由つき）。
- **IP 許可リストの遮断は効いている**（実測 2026-10-26: 自分の IP を含まない 1 件を入れると、未ログインの
  `/auth/me`・`/auth/login` は `403 IP_NOT_ALLOWED`、`/health` は除外で 200 のまま。反映は最大 15 秒）。
  以前 ⚠ に「保存はされるが遮断が効かない」と書いていたのは実体と違っていた。口は `ip-whitelist`、
  更新の本文は `entries: [{ cidr, note? }]`。
- **ただし自己ロックアウトの穴がある**（同じ実測）: 許可リストを入れた時点で管理セッションも遮断され、
  戻すための `PUT` 自体が 403 になる。画面には「現在 IP を追加」と注意書きがあり、人が自分を入れる前提。
  自動化・API 経由では戻す手が無い（DB を直接空にするしかない）。
- **その穴は 2026-10-27 に塞いだ**（d827）: 保存の入口が guard と同じ判定で、この接続の IP を含まない
  リストを **400 で断る**（保存しない）。空のリスト（制限の解除）は判定せず通すので、出口は常に開いている。
  画面の注意書きと「現在 IP を追加」はそのまま残る（押し忘れても締め出されない）。実測: 自分の IP を
  含まない `203.0.113.0/24` の保存 → 400 で一覧は空のまま。自分の IP の `/32` → 200。
  実装は 400 だが、保存できたことにする案（自分の IP を自動で足す）は人の指定を書き換えるため採らない。
