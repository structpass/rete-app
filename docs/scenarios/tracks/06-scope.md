# トラック 6 — スコープ（組織・プロジェクト・チャネル・社外ゲスト境界）

> 記法は [`../README.md`](../README.md)。範囲: 器（Space）の構造と所属。`/settings/organizations`（組織・プロジェクト・チャネルの 3 ペイン）と `/desk` のスコープ一覧。
> 対象外: 設定画面のその他の機能（→ トラック 5）。

## 0. この画面群の権限

- 段は **組織 ＞ プロジェクト ＞ チャネル**。組織は通常の作成 API を通るため**作成者がその組織の ADMIN になる**。プロジェクトとチャネルの設定画面は**管理者専用の作成 API** を使い、作成者への所属は自動では付かない（作っただけでは本人の `/desk` に出ない）。
- **組織の作成は誰でも可**。配下のプロジェクト作成は組織の管理者だけ、チャネル作成はプロジェクトの管理者だけ。
- **チャネル単独の権限は無い**。見えるかどうかは親プロジェクトの所属で決まる。
- 所属が無いものは **403 ではなく 404**（存在ごと隠す）。
- 社外の人（仕入先・運送・顧客）は**連携チャネルだけ**に所属させ、そこだけ見える状態にする。

### 1 チャネルだけを任せる時の進め方

**画面に見出し専用の導線は置かない**（d823 の確認で開発統括が「付けない」と決めた）。所属管理の画面（`/settings/memberships`）は管理グループごとの表のままで、個人の所属を付け外しする表は無い。**1 人を 1 チャネルだけに属させる経路は、いまは API だけ**。

1. システム管理者が `POST /memberships` に `scopeType=CHANNEL`・`scopeId=<チャネル>`・`role=ADMIN`・`accountId=<任せる人>` を送り、そのチャネルにだけ所属させる。
2. 本人はそのチャネルだけを使える。親プロジェクトと兄弟チャネルは見えない（直叩きも 404。実測 2026-10-27）。
3. 任せるのをやめる時は、そのチャネルの所属を `DELETE /memberships/{id}` で外す。

- **プロジェクトの管理者では足りない。** プロジェクトの管理者にすると配下の全チャネルが見える（権限が上がる）。逆に、プロジェクトの作成は組織の管理者でなければできない（`projects.service.ts`）ので、チャネルだけを任せる目的ではプロジェクト管理者にする理由も無い。
- **画面の入口はシステム管理者に限られる。** `/settings/organizations` と `/settings/memberships` はいずれもシステム管理者専用（`nav.ts` の `adminOnly`）。組織・プロジェクトの所属管理者はこの画面自体を開けないため、1 チャネルだけの付け外しは現状システム管理者が行う。
- **チャネルの管理者は最低 1 人を残す。** そのチャネル唯一の `ADMIN` は降格・削除がともに 400 で止まる（全消失ガード）。外す前に、後任を `ADMIN` にしてから外す。外す人が唯一の管理者のままだと、チャネルを消すまで外せない。

> **未確定**: 画面から「このチャネルだけ任せる」を付け外しできる導線は無い（d823 で付けないと決めた）。この手順は API での操作で、画面での操作は確かめていない。

### 事業部を新設する時の初期設定の進め方

**まとめて配る口は足さない**（d907 の確認で開発統括が「この方針でよい」と決めた）。既存の管理画面・管理グループ・個別所属を順に使い、立ち上げ範囲と権限を明示する。**器と分類の作成は手作業のまま残り、操作回数は一括にはならない。** 一度の処理で成功・取消しできるとも約束しない（操作漏れはチェック表と本人の確認で見つける）。

| 対象                   | 現在の実装                                                                                        | この手順での扱い                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 組織                   | 設定画面から通常の作成 API を通り、作成者に組織の直接 ADMIN 所属が付く                            | 作成者の所属を記録する                                       |
| プロジェクト・チャネル | 設定画面は管理者専用の作成 API。作成者への直接所属は自動では付かない                              | 作っただけで本人が `/desk` を使えるとは扱わない              |
| 人と権限               | 管理グループのメンバーはグループ管理、範囲の付与は所属管理の画面で扱う。個人の直接所属は API のみ | 事業部全体を使う人は管理グループ。例外は個別の直接所属（§1） |
| 分類                   | チャネルごとの分類。可視範囲外のチャネルには作れない                                              | 設定者の可視性を確保してからチャネルごとに作る               |
| 一括設定               | 組織のひな型・複製・一括所属追加の入口は無い（`POST /memberships/bulk` は 404）                   | 足さない                                                     |

1. システム管理者が、組織名・配下のプロジェクトとチャネル・各チャネルの分類・利用者と権限のチェック表を用意する。事業部全体を使う人と一部だけを使う人を区別する。新しいアカウントは既存の招待手順で先に用意する。
2. `/settings/organizations` で組織、プロジェクト、チャネルを順に作る。成功するたびに ID と名前を控える。途中で失敗したら一覧を再読込し、作成済みを確かめて未作成から再開する（同名の再送を安全とは扱わない）。
3. `/settings/groups`（グループ管理）で事業部全体を使う人の管理グループを作り、対象者を追加し、`/settings/memberships`（所属管理）で対象組織の役割を付ける。管理者と一般利用者の集合が違うならグループを分ける。既存グループの使い回しは既存メンバー全員の見える範囲が広がるため、メンバーを全件照合する。
4. 一部の範囲だけを使う人は、システム管理者が `POST /memberships` で必要な範囲だけに追加する（§0 の 1 チャネルだけを任せる時の進め方）。付与済みの直接所属と他グループの付与を合わせて確認する（外しても別経路が残れば見え続ける）。
5. 分類を設定する人が対象チャネルを見られることを確かめ、Desk のそのチャネルの「分類設定」で 1 つずつ追加する。一時的に所属を足す場合は、今回足した分と元からある分を控え、作業後に今回分だけ外す。そのチャネルの唯一の管理者を外す時は、後任を先に置く（§0 の 1 チャネルだけを任せる時の進め方）。
6. 一般利用者・限定範囲の利用者・非所属の利用者のそれぞれで、見えるチャネルと見えてはいけないチャネルを確かめる。分類の名前と件数をチャネルごとにチェック表と照合し、再読込後も残ることを確かめる。管理者だけで成功を判断しない。
7. 途中の失敗があると、保存済みの操作までは反映される（所属設定の保存も複数の付与を順に送る）。反映済みを再取得して不足分を進める。取り消す時は今回足した付与だけを外し、作った器は archive でしまう（S-SPC-06）。業務データの入った器・分類や既存グループは機械的に消さない。

> **未確定**: この手順を実データへ流した記録は無い（隔離した検証データでの作成・付与・分類設定・途中再開・後始末と、見える範囲の実確認は未実施）。

| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 前提   | 個人メモを持つ一般ユーザー（`wh-user`）と、システム管理者（`admin@rete.local`）。両方のセッションを先に用意する                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
