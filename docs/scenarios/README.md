# rete 業務シナリオ — 構成と記法

このフォルダは「そもそも通るか／想定できているか」を確かめるための資料群です。
デザインや挙動の機微ではなく、**業務として成立するか**と**期待結果が決まっているか**を見ます。
期待結果が書けない箇所は、そのまま仕様未確定として炙り出します。

## 1. 文書の役割

| 文書                                         | 役割                                                           | 読む人                   |
| -------------------------------------------- | -------------------------------------------------------------- | ------------------------ |
| [`cast-and-scenes.md`](./cast-and-scenes.md) | 世界観・登場人物・利用シーン（時間軸イベント）                 | シナリオを書く人・読む人 |
| [`tracks/`](./tracks/)                       | **トラック別のユースケースと実施ケース（この群の本体）**       | 検証する人               |
| [`index.md`](./index.md)                     | 入口。分類・観点の一覧、トラックの対応、仕様未確定の集約       | 全体像を知りたい人       |
| [`journeys/`](./journeys/)                   | 時間軸の物語として書いた詳細（P0〜P6）。ユースケースの根拠資料 | 背景を追う人             |

**正本は `tracks/` と `index.md`。** `journeys/` は物語としての根拠で、個々の期待結果を直す時は `tracks/` 側を直す。

## 2. トラック（タスク処理単位）

検証を回す単位で分ける。1 トラック = 1 つの仕事として着手・完了できる範囲。

| #   | トラック   | 範囲                                                           | ファイル                                           | 決定 |
| --- | ---------- | -------------------------------------------------------------- | -------------------------------------------------- | ---- |
| 1   | 認証       | ログイン・MFA・SSO・ログアウト・セッション                     | [`tracks/01-auth.md`](./tracks/01-auth.md)         | d771 |
| 2   | ホーム     | お知らせ・お気に入り・カレンダー                               | [`tracks/02-home.md`](./tracks/02-home.md)         | d772 |
| 3   | Desk       | チャット・タスク・昇格・器の切替                               | [`tracks/03-desk.md`](./tracks/03-desk.md)         | d773 |
| 4   | ファイル   | フォルダ・版管理・タグ・検索                                   | [`tracks/04-files.md`](./tracks/04-files.md)       | d774 |
| 5   | 設定       | メンバー・招待・監査・テナント・管理グループ・セキュリティ設定 | [`tracks/05-settings.md`](./tracks/05-settings.md) | d775 |
| 6   | スコープ   | 組織・プロジェクト・チャネル・社外ゲスト境界                   | [`tracks/06-scope.md`](./tracks/06-scope.md)       | d776 |
| 7   | 運用       | 障害・問い合わせ・運用イベント・横断メタ機能                   | [`tracks/07-ops.md`](./tracks/07-ops.md)           | d778 |

- 分担の目安は「その画面群を直す時に、同じ人がまとめて確かめるか」。跨るものは、期待結果が同じトラックへ寄せる。
- トラックを増やす時は、この表と `index.md` と決定を同時に直す。

## 3. ユースケースの記法

`tracks/*.md` の各表がユースケース。1 行 1 シナリオで、次の列を持つ。

| 列           | 書くこと                                            | 例                                           |
| ------------ | --------------------------------------------------- | -------------------------------------------- |
| ID           | シナリオ番号（既存を維持）                          | `S-AUTH-01`                                  |
| 見出し       | 何を確かめるか（1 文）                              | 通常ログインでセッションが確立する           |
| 分類         | §3.1 の語から 1 つ                                  | 正常系                                       |
| 観点         | §3.2 の語から 1 つ                                  | 操作反映                                     |
| ユーザー     | 誰が操作するか（役職まで）                          | 入荷担当（物流センター）                     |
| 立場         | §3.3 の語。権限の位置づけ                           | システムMEMBER／所属MEMBER                   |
| 状況         | その操作に至る事情（なぜ今それをやるか）            | 朝の検品前に当日の予定を確認したい           |
| 画面操作要領 | 画面・導線・操作の順（画面が無いものは API と書く） | `/login` → メール・パスワード入力 → ログイン |
| 期待結果     | 断定で書く。断定できない時は ⚠ と理由               | ホームへ遷移し、セッションが残る             |

### 3.1 分類（何を確かめる種類）

| 語           | 意味                                                     |
| ------------ | -------------------------------------------------------- |
| 正常系       | 想定どおりの使い方で業務が成立する（幸せ道）             |
| 認可境界     | 権限の外側の人が拒否される・見えない                     |
| 入力検証     | 不正・欠落・境界値の入力が拒否される                     |
| 運用イベント | 退職・異動・交代・障害など、時間軸で起きる出来事への追従 |
| 状態整合     | 二重操作・同時操作・再実行で壊れない（冪等・排他・連鎖） |
| 未確定       | 期待結果が決まっていない（仕様課題。⚠ を付ける）         |

### 3.2 観点（何を見るか）

| 語           | 見るもの                                 |
| ------------ | ---------------------------------------- |
| 画面表示     | 見える・見えない、並び順、状態の出し分け |
| 操作反映     | 保存・更新が次の表示に反映される         |
| 権限可否     | 通る／403・404 で拒否される              |
| 通知・バッジ | 未読・件数・知らせが正しく動く           |
| 永続化       | 再読込・再ログイン後も残る               |
| 越境遮断     | 所属外のデータが見えない・直叩きできない |
| 監査・記録   | 操作ログに残る、追える                   |
| 復旧・縮退   | 失敗した時に何が起きるか、戻せるか       |

### 3.3 立場（権限の位置づけ）

現行の権限は **2 軸**（ADR 0077 で業務ロール層を撤去済み）。

1. **システムRole** — `ADMIN`（テナント管理全般）／`MEMBER`
2. **所属** — 組織・プロジェクト・チャネルの membership、管理グループ経由の grant

| 語             | 意味                                             |
| -------------- | ------------------------------------------------ |
| 未ログイン     | セッションが無い                                 |
| システムADMIN  | テナント管理者。管理系 API を全て通る            |
| システムMEMBER | 管理系は 403。日常機能は所属に従う               |
| 所属ADMIN      | 対象スコープの管理者（作成・改名・参加者管理）   |
| 所属MEMBER     | 対象スコープの一員（読み書きは機能による）       |
| 非所属         | 対象スコープの membership が無い（存在ごと隠す） |
| 社外ゲスト     | 連携チャネルだけに参加する社外の人               |

- **システムADMIN でも他人の個人メモ・DM は見えない**（プライバシー境界）。この非対称は期待結果に必ず書く。
- 立場が 2 つ以上あるシナリオ（例: ADMIN と MEMBER の対比）は、**主役を「ユーザー」に、対比を「状況」に書く**。

## 4. 実施ケースの記法

ユースケースを実際に試す手順。`tracks/*.md` の §ケース に置く。1 ユースケースに 1 つ以上。

| 列       | 書くこと                                                         |
| -------- | ---------------------------------------------------------------- |
| ケースID | `<ユースケースID>-C1`（2 つ目は 開発エージェント）               |
| 前提     | 必要なデータ・状態（seed ユーザー、既存データ、前提ケース）      |
| 手順     | 番号付きの操作。画面なら押す順、API なら叩く順                   |
| 期待     | 各手順の後に何が見えるか（ユースケースの期待結果を手順に落とす） |
| 後始末   | 作ったデータの消し方（無ければ「なし」）                         |
| 実行     | 下の 3 つから 1 つ                                               |

| 実行         | 意味                                                                             |
| ------------ | -------------------------------------------------------------------------------- |
| `自動 @タグ` | E2E で自動実行する。タグは `e2e/features/*.feature` の `@...` と一致させる       |
| `手動`       | 人が画面で確かめる。E2E 化できない理由（外部スタック・メール・時刻など）を添える |
| `対象外`     | 実施しない。理由（仕様未確定・機能が無い・廃止済み）を添える                     |

- 手順は**第三者が読んで同じ結果を再現できる粒度**で書く。押す場所は画面名と要素名まで。
- 期待は 1 手順につき 1 つ。まとめない。

## 5. 状態の持ち方

ユースケース表の末尾に 3 値で持つ。

| 記号 | 意味                                         |
| ---- | -------------------------------------------- |
| ⬜   | 未確認（初期値）                             |
| ✅   | 通ることを確認済み（自動なら直近の実行が緑） |
| ❌   | 通らない（不具合。決定を立てて直す）         |

- ⚠ は状態とは別軸。「通るかどうか以前に、正解が決まっていない」を表す。⚠ が付いたユースケースは状態を ✅ にしない。
- 状態は**実行の結果でだけ**更新する。読んで判断しない。

## 6. 更新の手順

1. 画面や API を変えたら、まず該当トラックのユースケース表を直す（`journeys/` より先）。
2. 実施ケースを足す・直す。`実行` 列が `自動` なら、同時に E2E の feature を直す。
3. `index.md` の件数と仕様未確定一覧を直す。
4. E2E を実行し、緑／赤を状態へ反映する。赤は不具合として決定を立てる。

### トラックを閉じる前に

**トラックの決定を閉じると、その中に残したものは台帳の並びから消える。** 閉じる前に、⬜（未確認）と ⚠（未確定）の行を**別の決定として起票**し、番号を `index.md` の「次にやること」へ書く。

- まとめて 1 件でよい（トラックごとに 1 件）。
- 起票せずに閉じると、残りはどこからも拾えなくなる（`hub dirty` も拾わない）。
- 実際に起きたこと（2026-10-26）: 8 トラックを閉じた後、未確認 11 件・未確定 14 件が台帳から消え、番号を振り直して戻した。
