# 開発用語集（開発統括向け）

> 開発エージェントが rete 開発でよく使う用語を、非エンジニアの開発統括が読んで分かる平易な言葉でまとめたもの。過去の作業ログ・チケット・memory・規約から収集（2026-06-24 作成）。
>
> 困ったらカテゴリ見出しから引いてください。各用語は「概要（平易な説明）」だけ読めば足ります。

---

## 1. 開発フロー（Decision Hub の1件処理）

開発エージェントの開発は Decision Hub（`D:\Dev\hub`）のチケット1件ごとに進む。現行の入口は 3 本だけ。1件を仕上げるのが `dev-work`、確認ありを閉じるのが `dev-check`、点検・起票・整備が `env-inspect`。判断の記録は `dev-adr` が担う。v1 の「設計 → 承認 → 製造 → 確認」と、それを担った `/dev-plan`・`/dev-design`・`/dev-code`・`/dev-decide`・`/dev-discover`、および旧入口の `dev-ticket`・`dev-review`・`maint-log` は退役して使わない。

### /dev-plan（プラン）— 退役済み

退役済み。現行は着手前の承認ゲートを置かない。`dev-work` が 1 件を最後まで通し、開発統括が疑義を申し出る可能性がある時だけ確認ありに上げる。

### /dev-design（デブデザイン｜設計フェーズ）— 退役済み

v1 は着手前の設計工程で、チケットを設計して開発統括の承認待ちに置いた（「要設計」→「設計済」）。現行は着手前の承認ゲートを置かず、`dev-work` が着手時に要求と検査の内容を決定に固定する。変更が4本以上または構造を動かす時は、plan を確定する前に `design-reviewer` が設計の前提を実体で裏取りする。

### /dev-code（デブコード｜製造フェーズ）— 退役済み

v1 は開発統括の承認後に回ってきたチケット（「要製造」）を受け取り、実装・検証・コミットまで完遂した。現行は `dev-work` が実装・検証・証跡の登録・コミット・完了までを1件で通す。

### /dev-decide（デブデサイド｜確認回答フェーズ・開発統括手番）— 退役済み

v1 は「要確認」のチケットを開発統括が一問一答でまとめて回答するための開発統括専用スキルだった。現行は、開発統括が疑義を申し出る可能性がある決定だけを確認あり（check）に置き、`dev-check` で 1 件ずつ会話して閉じる。追加対応が要れば、元の決定は顛末を書いて閉じ、新しい決定を open で立てる。

### 点検（旧 /dev-review）— 退役済み

退役済み。現行の点検は `env-inspect`（観点 × 対象の点検表から選ぶ）で行い、見つけたものは決定として置く。実装者とは別の主体による独立確認は `dev-work` の独立の目で行う。

開発の実施状況ドキュメント（build-status.md）の鮮度は、git の実績と突き合わせる専用の技能（build-status-freshness-audit）が見る。

### /dev-discover（ディスカバー）— 退役済み

v1 は要件が曖昧なとき、短い質問のやり取りで「何をどこまで作るか」を固めた。現行は起票の時に目的と期待結果（`ui_metadata.intent`）を書き、開発統括の判断が要る点だけを `user_decision` の停止で問う。

### /chk-rete（チェックレテ）

rete の開発サーバー（画面側 :3010 / サーバー側 :3011）を再起動してヘルスチェックを行う1コマンド。実装後に必ず実行し、起動が壊れていないか確認する締めの操作。

## 2. Co-driver（共走）— 開発統括が判断する場面

AI は勝手に押し切らず、開発統括が決める場面（方向性・不可逆な操作・受入）では止まって相談する。「作ってから違う」を防ぐ。

### 正解像（せいかいぞう）

「どうなったら正解か」という完成の定義。AI が着手時に検査の内容として決定に書き、決定台帳で読める。**開発統括が疑義を申し出る可能性がある時だけ**、この基準に沿って確認ありに上げる（基準は §3 の補足）。

### 実行承認（じっこうしょうにん）— 退役済み

Board v1 の工程。開発統括が Board の「承認」ボタンを押すまで実装を始めない、という唯一の着手ゲートだった。Board 自体も 2026-10-18 に廃止した。現行の Decision Hub に一律の着手前承認ゲートは無い。AI は着手すると実装・検証・完了までを内部で進め、開発統括が疑義を申し出る可能性があるもの（方針や仕様の内容・戻せない操作・業務の流れ）だけを確認ありに上げる。

### co-driver（コードライバー）

開発統括を運転席の隣（co-driver）に置く開発スタイルの呼び名。承認ペース（実行承認ゲート）は退役したが、開発統括が決める場面で AI が止まることは変わらない。一方的な自律実装はしない。

### 設計ラリー（せっけいラリー）

AI と開発統括が一問一答を繰り返しながら要件・設計を固めていく作業。合意が固まるたびに仕様書と Decision Hub の要求・実行記録へ残し、会話だけに頼らない（後述の compact で消えないように）。

### choice-card（チョイスカード）— 廃止済みの Board の機能

旧 Board で 開発エージェントがチケットに置いていた「二択カード」。A案・B案を開発統括が1クリックで選べる。**押してもチケットの状態は変わらない**（相談の道具。状態を動かす操作ではない）。

## 3. 決定の状態（ステータス）

作業を管理する正本は Decision Hub。状態は次の3つだけ。

| 状態              | 意味                                                  | 次の手番                                       |
| ----------------- | ----------------------------------------------------- | ---------------------------------------------- |
| open（未対応）    | AI が調査・実装・検証を進める。前提待ちや未完了も含む | AI が次の行動を記録する                        |
| check（確認あり） | 開発統括が判断する材料がそろっている                      | 開発統括の最新の明示回答を受け、dev-check で閉じる |
| done（完了）      | 必要な検証・独立確認を終え、顛末を記録した            | 追加要求は新しい決定にする                     |

確認不要なら AI が検証後に done にする。方針・価値・対外的約束・未許可の不可逆操作・業務の流れに影響する判断は、質問・見る場所・良しとする状態・変更前・変更後をそろえて check に置く。必要な検証や材料が足りなければ open のまま次の行動を残す。

旧 Board の active / waiting / closed や待ち理由、受入ボタンは廃止済みで、現行の状態・操作には使わない。

## 4. Decision Hub / Backlog（作業の台帳）

### Decision Hub（決定台帳）

要求・実行・検査・独立確認・顛末を記録する現在の台帳。操作の正本は [台帳の案内](../../../hub/README.md)、Codex からの利用手順は [操作案内](../../../docs/decision-hub-for-codex.md) を参照する。

### Backlog（バックログ）

残っている作業の総称。現在の未対応は Decision Hub で読む。開発トラックの索引は [開発バックログ](backlog.md)。Rete の Backlog タブを開く操作ではない。

### system（対象）

決定が対象とする製品・範囲。新しい記録の値は rete / reference / cross。旧 Board の分類値を新規の記録へ流用しない。

### 検査と独立確認

実施した検査の結果・根拠と、実装者とは別の AI が確認した対象版・所見を台帳に残す。未実施を合格にしない。

### 進め役（claim / release）

同じ決定を二重に進めないため、着手前に自分の一意なセッションで claim する。他者が所有中なら入らない。区切る時は次の行動や顛末を残して自分の所有だけを release する。旧 Board の run・編集権 API とは別の仕組み。

### Board（ボード）— 廃止済み

旧チケット管理ツール（instruction-board）。2026-10-18 に廃止し、Rete の Backlog タブも削除した。過去の履歴は退避先で参照するが、起票・実行・完了の手順には使わない。

## 5. チケット採番（ID の読み方）

現行の決定は Decision Hub の D 番号で読む。以下は過去ログを読むための旧 Board の採番で、新規には使わない。旧 ID は `<3文字>-<4桁連番>` の形（例 `dsk-0174`＝Desk の174番）。先頭3文字がサブシステムを表す。

| 接頭辞 | 指すもの                              |
| ------ | ------------------------------------- |
| dsk-   | Desk（チャット×タスク機能）           |
| fil-   | Files（ファイル共有・版管理）         |

| set-   | Settings（テナント運営管理）          |
| cmn-   | Common（認証・権限など横断共通基盤）  |
| brd-   | Board ツール自身（instruction-board） |
| ref-   | struct-pass-reference（参照システム） |

## 6. 開発トラックと進捗ドキュメント

### トラック

rete 開発を機能領域で束ねた管理単位。`desk / files / home / settings / hardening / common` がある。各トラックは計画書と進捗報告書のペアで管理される。

### build-plan.md（計画書）

そのトラックで「何を・どの順番で・どこまで作るか」を定義した骨格。進捗では書き換えない。

### build-status.md（進捗報告書）

そのトラックで実際に何が完了・進行中・未着手かの記録。git の実績と照合して更新する。将来は廃止予定（現在は延命中）。

### devplan-sources.json

旧 Board が計画書・報告書を読み込むために使った設定ファイル。Board とともに退避済みで、現役の設定ではない。

### hardening（ハードニング）

「堅牢化」の意味。本番公開に向けてセキュリティや堅牢性を強化する作業の総称（認証強化・権限制御の徹底・入力検証・不正ログイン対策など）。

## 7. 設計・意思決定の記録

### ADR（Architecture Decision Record）

重要な設計判断を残す記録。**採用した案だけでなく、検討して捨てた案と理由も**残す。後から同じ議論を繰り返さないため。`docs/decisions/0044-...` のような番号付きファイル。

### ADR 0044 — 退役した体制の記録

2026-06-22 確定の開発フロー大改訂の記録。旧フロー（/dev-loop・/dev-next・/dev-storming）を廃止し、`/dev-design`・`/dev-code`・`/dev-decide` の3スキル体制と6つの状態（要設計・設計済・要製造・製造済・要確認・Close）へ移行したことを定義した。**その体制は退役しており**、現行の入口は `dev-work`／`dev-check`／`env-inspect` の 3 本（判断の記録は `dev-adr`）。この節は当時のフローがどう変わったかの記録として読み、v1 の手順を現行として使わない。

### /dev-adr（デブ・エーディーアール）

「規約からの意図的な逸脱」「複数案からの選択」「既知の不完全さの許容」「外部制約による選択」が起きたとき、その判断を ADR として記録するコマンド。

### 単一ソース（Single Source of Truth）

ある情報について「ここだけが正しい」とされる唯一の保存場所。複数箇所に同じ情報があると食い違うため、必ず1箇所を正本に定める。

### モデルタブ（正本）

rete 固有の共通仕様（UI ルール・用語・画面命名など）を一元管理する唯一の正本。アプリの `/model` 画面で閲覧でき、開発エージェントは実装前にここを読む。

### 捨て案 / negative knowledge

「試したが採用しなかった案とその理由」の記録。同じアイデアを後で別セッションが再び試して時間を無駄にしないための予防。

### 可逆性テスト（two-way door / one-way door）

ある判断が「1回の改修で別案に切り替えられるか（two-way＝可逆）」「切り替えると大コスト（one-way＝不可逆）」かを見る考え方。可逆なら 開発エージェントが自走決定、不可逆なら開発統括に確認。

## 8. 品質チェックとレビュー

### scale（スケール）— Tiny / Small / Medium / Large

変更の規模を4段階で分類するラベル。変更ファイル数が目安（Tiny＝1行修正、Small＝バグ修正、Medium＝新機能、Large＝16ファイル超の大規模）。スケールごとに手順の厳密さが変わる。

### quality cycle（品質サイクル）

実装後に複数のレビュー AI を同時に走らせ、問題を見つけて直す反復プロセス。Medium は最大2回、Large は最大3回。重大な問題が残れば次の回へ。

### ins-code / ins-security / ins-db

それぞれ「コード品質」「セキュリティ」「データベース」を専門に検査する点検の道具。`env-inspect` から呼ぶ（旧名 code-reviewer / security-reviewer / database-reviewer は退役）。

### CRITICAL / HIGH / MEDIUM / LOW（深刻度）

検出した問題の重大さの4段階ラベル。CRITICAL/HIGH は**必ず直してから**コミット・完了宣言する。MEDIUM/LOW は別チケットに退避して後回し可。

### /rev-arch・/rev-integrity・/rev-quality

コードを点検する3つのレビューコマンド。arch＝**構造**（設計ルール違反）、integrity＝**整合性**（命名の揺れ・ドキュメントとのズレ）、quality＝**品質**（セキュリティ・テスト・不要コード、修正まで実行）。

### drift（ドリフト）

ドキュメントとコードの実態が食い違っている状態（例：実装済みなのに「未着手」と記録されたまま）。「漂流」が語源。見つけたら**必ず是正**する。

### ins-dead-code

使われていない関数・依存ライブラリ・ファイルを自動検出して安全に削除する道具（旧名 refactor-cleaner は退役）。

## 9. 完了の検証（UI 変更時）

### UI Verification Gate（UI 検証ゲート）

画面の見た目や操作を変えた実装は、完了を宣言する前に**必ず1回は実際の画面を確認する**という決まり。スクショ比較か実ブラウザ操作で確認する。過去に「画面を見ずに完了」して差し戻しが32件出た反省から導入。

### 証跡駆動の完了検証

rete の UI チケットでは、完了時にスクショ等の証拠（証跡）を決定の検査記録から辿れる場所に残すルール。「言った・言わない」の解釈ズレを証拠段階で防ぐ。

### before/after スクショ

変更前（before）と変更後（after）の画面写真。証跡添付に使う。

### verification-before-completion（完了前検証）

「動いた」と報告する前に、検証コマンドを実際に実行して出力を確認してから完了宣言するルール。「たぶん動いてる」で終わらせない。

## 10. アーキテクチャの約束事（不変条件）

コードの構造が崩れないための7つの約束。開発統括が直接触ることはないが、開発エージェントのコミットでよく出てくる。

### DTO 境界

API がデータを返すとき、データベースの内部形式をそのまま渡さず、専用の「送信用の形」（DTO）に変換してから返す約束。情報漏れと型ズレを防ぐ。

### Repository 分離

データベースへのアクセスを専用の窓口（Repository）に集約し、業務ロジックが直接 DB を叩かない約束。変更の影響範囲を限定できる。

### 2モジュール目の法則（コピペ禁止）

2つ目の機能が1つ目と80%以上同じなら、先に共通部品を抽出してから作る。「あとで共通化」は禁止（来ないため）。

### エラーハンドリングの一元化

各機能で個別にエラー処理を書かず、上位の共通受け口に集める。個別に書くと必ずどこか漏れる。

### shared 型の整合性

共通定義した「型（データの形）」は必ずどこかで使う。「定義したが未使用」は設計意図の嘘で、後で負債になる。

### hook 抽出

同じ画面パターンが3ページ以上で重複したら、共通部品（hook）に切り出す。

### 完了基準チェックリスト

機能の「完了」を宣言する前に確認する必須項目一覧。全項目に✅がついて初めて完了とみなす。

## 11. 用語ミニ辞典（その他よく出る語）

### CRUD（クラッド）

Create（作成）/ Read（読取）/ Update（更新）/ Delete（削除）の頭文字。データ操作の基本4種。「CRUD を作る」＝一覧・詳細・登録・編集・削除の一式を作る。

### ORM / Entity

ORM＝コードでデータベースを操作する変換ライブラリ（rete では Prisma）。Entity＝DBの1行に対応するデータの塊。Entity を外にそのまま返さないのが DTO 境界。

### migration（マイグレーション）

データベースの構造（テーブルや列）を変更する履歴スクリプト。段階的に適用してバージョン管理する。

### seed（シード）

開発環境を動かすための初期データ（管理者アカウント・サンプルデータ）を一括投入するスクリプト。

### env var（環境変数）

パスワード・接続先など「コードに直書きしてはいけない値」を外部から渡す仕組み。`.env` ファイル等で管理し、本番と開発で切り替えられる。

### healthcheck（ヘルスチェック）

サーバーが正常稼働しているか確認する専用 URL。監視ツールがここを叩いて死活を見る。

### dev watchdog（デブウォッチドッグ）

ローカル開発サーバーの稼働を監視し、必要に応じて復旧する仕組み。現在の対象・周期は実際のタスク設定とローカル運用資料で確認する。廃止済みの Board を稼働対象に戻さない。

### fire-and-forget

バックグラウンド処理の方式で「実行したら結果を待たない（失敗しても全体を止めない）」設計。失敗時はログにエラーを残すだけ。

### compact / context

context＝開発エージェントが今の会話で参照できる記憶の総量。長くなると限界に近づき、古い会話を要約圧縮するのが compact。要約で合意が消えるため、重要事項はファイルに書き出しておく。

### sub-agent（サブエージェント）

メインの 開発エージェントから独立した別の AI（実働担当）。`ins-code` などを呼ぶ時に使う。別の記憶で動くのでメインの記憶を消費せず、安価なモデルに固定されている（本用語集もサブエージェントが収集）。

### permission / sandbox

Claude Code の実行制御の2層。permission＝「このコマンドを実行してよいか」の承認、sandbox＝OS レベルで実行できる操作の物理的な制限箱。許可ボタンを押しても sandbox の箱は開かない。

### 並列セッション

複数の 開発エージェントが同時に動いている状態。同じチケットの二重作業は、着手時に `start` で取得し `yield-edit-rights` で返す run の編集権が防ぐ。

### surgical changes（外科的変更）

依頼に直接関係しないコードは触らない約束。「ついでに直す」を禁止し、変更範囲を最小に絞る。

## セキュリティ用語

### RBAC（ロールベースアクセス制御）

「管理者（ADMIN）／一般メンバー（MEMBER）」などの役割に応じて、できる操作を制限する仕組み。

### RLS（行レベルセキュリティ）

データベースの行（レコード）単位でアクセス制御する仕組み。「自分のデータだけ見られる」を DB レベルで強制する。

### OIDC / SSO

OIDC＝「どのサービスでも同じアカウントでログイン」できる標準の仕組み。SSO（シングルサインオン）＝1回ログインすれば他システムにも自動ログインできる状態。rete にログインすると struct-pass-reference にも入れる。

### MFA / TOTP（二段階認証）

パスワードに加え、スマホの認証アプリのワンタイムコードでもログインを確認する方式。

### IDOR

本来見られないはずの他人のデータに、ID を直接指定してアクセスできてしまう脆弱性。

### XSS

攻撃者が悪意あるプログラムをページに埋め込み、他のユーザーのブラウザで実行させる攻撃。

### OWASP Top 10

ウェブアプリのセキュリティリスク上位10種の公式リスト。`ins-security` がこれを基準に検査する。
